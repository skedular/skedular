# Implementation Plan: Organization Patch Updates

## Summary

Use one field-masked `Update*` contract per migrated organisation update surface. GraphQL organisation setup editing uses `updateOrganization` with explicit enum-list field selection through `fieldsToUpdate`; the specialised GraphQL organisation update surfaces follow the same model, and migrated organisation gRPC billing details, tag, custom tag, product tag, and zone updates keep normal `Update*` RPC names with field masks. The implementation removes dead full-replacement update paths and the temporary public `*Patch` aliases, distinguishes omitted values from clear/default values, relies on existing entity-layer concurrency protection with reload-and-retry for selected fields, accepts valid no-op partial updates by returning the latest state, and emits structured logs for success, rejection, retry, and failure paths.

## Technical Context

**Language/Version**: C# .NET 10 for organisation API/domain services; GraphQL schema generated by HotChocolate/Fusion tooling; TypeScript/React/Relay only if web caller artifacts are updated  
**Primary Dependencies**: HotChocolate GraphQL mutations, Organization.Api service layer, Organization.Shared repository/model layer, generated GraphQL schema/Relay artifacts, structured logging via existing Microsoft/Serilog conventions  
**Storage**: PostgreSQL via EF Core; no new migration planned because all editable organisation setup fields already map to existing organisation fields/metadata
**Testing**: xUnit unit tests for API/service behaviour; organization-domain integration tests for GraphQL mutation contract and persistence through repository/query-layer assertions; Vitest/React Testing Library for the web forms that consume field-masked update mutations
**Target Platform**: Organisation API service and web GraphQL clients in the Skedular monorepo  
**Project Type**: Organisation backend GraphQL/gRPC contract and service change with required web Relay consumer updates across `webapp`, `webapp-teams`, and `webapp-spaces`
**Performance Goals**: Single-field inline save completes within the existing organisation update latency envelope; no extra full-object fetch from the client is required before submitting a patch  
**Constraints**: Must preserve omitted fields, distinguish omitted from explicitly cleared/default values, rely on existing entity-layer concurrency handling without requiring a caller-supplied version token, accept no-op patches by returning latest details, remove dead full-replacement update paths, and keep one public update contract name per migrated surface
**Scale/Scope**: Organisation-domain GraphQL update surfaces plus migrated gRPC billing details, tag, custom tag, product tag, and zone update endpoints; field masks stay explicit in each update input

## Constitution Check

- [x] **I. Contract-First** — This feature changes the organisation GraphQL contract. `scripts/generate-graphql.sh` must be run after schema changes. If web Relay mutations consume the new contract, regenerate web Relay artifacts with the existing web generation flow rather than hand-editing generated files.
- [x] **II. Domain Boundaries** — Scope stays inside the organisation domain. No direct cross-domain database access is planned. Organisation gRPC contracts are updated only where their update endpoints are migrated to field masks.
- [x] **III. Testing** — Unit tests are required for field-selection, no-op, concurrency retry, allowlist, authorisation, validation, and logging paths. GraphQL integration tests are required because the public schema and persistence boundary are crossed; assertions must use repository/query-layer methods, not raw `DbContext`.
- [x] **IV. Frontend** — Web UI changes are in scope for all three web apps. Relay fragments/mutations must be collocated, generated Relay artifacts must not be hand-edited, typography must come from `@skedular/ui`, shared runtime helpers from `@skedular/shared`, and user-facing copy must use British spelling.
- [x] **V. Pattern Consistency** — This introduces the organisation-domain partial-update pattern. The plan documents explicit field selection plus an allowlist rather than implicit null semantics, so later domains can reuse it deliberately without duplicating update contracts.
- [x] **VI. Logging** — Structured logging is planned for patch start/completion, field selection/no-change/concurrency-retry/invalid-field decisions, authorisation failure, validation failure, and persistence failure paths. Logs must include correlation context and omit sensitive payload values.
