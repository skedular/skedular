# Implementation Plan: Smart Organization Landing Page

**Branch**: `015-smart-org-landing-page` | **Date**: 2026-05-24 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/015-smart-org-landing-page/spec.md`

## Summary

Add a smart organization landing page to webapp-teams, webapp-spaces, and webapp. When a user
visits the root landing page (`/`) and has not yet selected an organization, they see an
org-selection panel (1+ orgs) or a create-org prompt (0 orgs) — both in a centered, no-nav
layout with the left sidebar completely absent from the DOM. No auto-redirect; the user must
actively choose. Onboarding redirect (to the welcome page) takes priority over the panel.

## Technical Context

**Language/Version**: TypeScript 6.0.3, React 19.2.6, Next.js 16.2.6 App Router  
**Primary Dependencies**: Relay 20.1.1, MUI v9, `@skedular/ui`, `@skedular/shared`, `pnpm 11`, `Turborepo`  
**Storage**: N/A — read-only GraphQL query, no persistence changes  
**Testing**: Vitest + React Testing Library (`pnpm test` per app)  
**Target Platform**: Three web apps: `webapp`, `webapp-teams`, `webapp-spaces`  
**Project Type**: Frontend-only (web application)  
**Performance Goals**: No new backend calls; single page-level query (`myOrganizations`) added to landing page load  
**Constraints**: Must not modify backend contracts; `pnpm relay` must be re-run after fragment source changes; no hand-edited generated `*.graphql.ts` files  
**Scale/Scope**: Three webapps, two new components, three modified root shells, three modified landing pages

## Constitution Check

_GATE: Passed. Re-evaluated after Phase 1 design — no violations._

- [x] **I. Contract-First** — No `api-definitions/` changes. The `myOrganizations` query and
      `MyOrganizationDetails` type already exist. New Relay fragment source files are authored
      in the web apps; `pnpm relay` is run per app to regenerate typed artifacts.
- [x] **II. Domain Boundaries** — Frontend only. The `myOrganizations` data comes from the
      Organization domain through the existing Fusion GraphQL gateway. No backend cross-domain
      concerns.
- [x] **III. Testing** — Vitest + React Testing Library. Unit tests planned for
      `NoOrganizationLandingContent` in both webapp-teams and webapp-spaces covering all three
      states (0 orgs, 1 org, N orgs) and the `hideSideNav` prop behavior. No persistence
      boundary crossed; no integration tests required.
- [x] **IV. Frontend** — Relay fragment colocation maintained (fragment declared inside the
      component). Generated `*.graphql.ts` artifacts not hand-edited. Typography uses
      `@skedular/ui` wrappers (`LeadIconTypography`, `CaptionIconTypography`,
      `BodyIconTypography`). American spelling used in all UI copy (user preference override
      per session memory).
- [x] **V. Pattern Consistency** — No new patterns. Page-level `useQueryLoader` pattern matches
      existing `pageHome_rootQuery` in webapp. `hideSideNav` is a minor, additive prop
      extension of the existing `NoOrganizationRootShell` API.
- [x] **VI. Logging** — Per LOG-001–LOG-003 in the spec: client-side structured log (console +
      existing client logger) on landing page mount recording which state was shown (no-orgs,
      single-org, multi-org), org count, and user ID if available.
