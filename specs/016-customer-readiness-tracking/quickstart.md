# Quickstart: Customer Readiness Tracking

## Prerequisites

- Work on branch `016-customer-readiness-tracking`.
- Read `AGENTS.md`, `shared/Api.Shared/AGENTS.md`, and `shared/Api.Shared.Clients/AGENTS.md` before touching event
  contracts or metadata companions.
- Do not edit generated event outputs under `shared/Api.Shared.Clients/obj`.

## Implementation outline

1. Add `customer_readiness_v1_key.proto` and `customer_readiness_v1_value.proto` under
   `api-definitions/events/skedular`.
2. Run `api-definitions/events/generate.sh`.
3. Add the handwritten metadata companion under
   `shared/Api.Shared.Clients/Events/Skedular/CustomerReadiness/V1/CustomerReadinessMetadata.cs`.
4. Add a customer-readiness publisher abstraction in shared code that participating processors can register.
5. Extend booking, organisation, team, marketplace, and location `CustomerSubscriber` handlers to publish
   `CustomerIdentityProvisioned` after durable local customer provisioning succeeds.
6. Add customer-domain readiness persistence: aggregate, domain-state collection/table, repository queries, migration,
   required-domain service, and readiness derivation service.
7. Add a customer processor subscriber for `customer_readiness`.
8. Replace backend readiness/auth fan-out with the customer-domain readiness lookup.
9. Extend or reuse the customer workaround republish path so operators can manually trigger customer
   synchronisation/backfill.
10. Add structured logs and tests before considering the feature complete.

## Acceptance checklist

- `customer_readiness` exists as a customer-owned public topic.
- `CustomerIdentityProvisioned` payload has only `customerId` and `domain`.
- Readiness domain enum contains only booking, organisation, team, marketplace, location, and any other confirmed
  current non-customer participant added during implementation.
- Generated event outputs were regenerated by script, not edited by hand.
- Participating domains publish only after local provisioning succeeds.
- Customer domain consumes readiness events idempotently and stores per-domain state as a collection.
- Missing central readiness blocks access; no backward-compatible legacy fan-out fallback remains.
- Manual customer synchronisation/backfill republish flow produces readiness state through participating domains.
- Logs cover publish, consume, duplicate/replay, activation, blocked access, manual sync, and failure paths.
- Tests cover partial activation, full activation, duplicate reports, replay/backfill, missing state, active
  non-regression, no publication for unmappable domains, publish-after-provisioning, and single-source readiness lookup.
